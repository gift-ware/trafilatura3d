## Functional reference

The names of the nodes' parameters, their ranges and menus, and the visible behaviour of the editor follow the public
documentation of Substance 3D Designer and Substance 3D Painter (Adobe Experience League), so that users of those
tools find a familiar workflow. The documentation page each node follows is listed below. Behaviour, parameter names
and file formats are functional elements; the implementations behind them are ours.

`reference/` is the functional index of that documentation, used by the conformance tests: for each node its
identifier, name, category and page URL, its ports, and its parameters with type, default, range and menu items. It
holds no text of the documentation.

## Interoperability

The importers read the user's own project files, for interoperability: `.sbs` packages (`trafilatura3d/sbs/`) and
`.spp` projects (`trafilatura3d/spp/`). Their formats were studied from such files and from public documentation, only
to read the data they hold. No program was decompiled, disassembled or modified, and compiled formats (`.sbsar`) are
never read, including those embedded in `.spp` projects. To let imported files work, our nodes and brush alphas are
tuned to respond to the same parameters in the same way, by comparing their visible output; the methods that produce
it are our own.

`trafilatura3d/sbs/library.json` is the importer's correspondence table: for each graph of the Designer library that a
user's file can reference, its identifier and those of its parameters, inputs and outputs mapped to our node type and
parameter keys, enumeration values mapped to our choices, and the default values where they differ from ours (a .sbs
file does not store parameters left at their default). It contains identifiers and numbers only, no graphs, labels,
descriptions or other content of Adobe, and exists so that imported files open and look the same without Designer
installed.

A few functions of the function library (`trafilatura3d/functions.py`) must give exactly the results that imported
graphs expect, because those graphs call them by name and read what they compute: the non-square output size
functions (both versions) and the tile count function, which set the variables a noise reads (scale per axis, size
ratios, render region), and the weight of each Stamp Map level for a roughness value (also used by
`fxmap.level_weights`). They reproduce that behaviour exactly, as the format requires, and exist only for
interoperability, like the correspondence table.
